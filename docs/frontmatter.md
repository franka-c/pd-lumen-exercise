# The front-matter contract

Every markdown file that an agent should be able to find and trust carries YAML
front-matter. This is the only contract in the system. `discovery.yml`, the
staleness check and the pull request blast radius are all derived from it. The
index is regenerated by the author before every pull request and checked by CI, so a
file without front-matter is invisible to all three.

## Deliverables

```yaml
---
deliverable: 05-information-architecture   # reference number from the playbook
project_number: 4                          # the number on this project's cover
status: confirmed                          # draft | in-review | confirmed | superseded
owner: designer                            # pm | designer | architect
updated: 2026-09-25                        # the day the content last changed
confirmed_with_client: 2026-09-25          # omit until a client review confirms it
depends_on: [01-project-alignment, 03-user-personas]
feeds: [06-feature-prioritization, 07-technical-solution-proposal, prototype]
decisions: [D-014, D-021]                  # entries in log/decisions.md
figma: https://figma.com/file/...          # when the real artifact is a board
figma_checked: 2026-09-25                  # the day the write-up was last reconciled with it
---
```

## Answering a staleness flag

A deliverable is flagged stale when something it `depends_on` changed after the
deliverable was last reconciled. There are two honest answers.

**It needed changes.** Make them and bump `updated`. Its own dependents are then
flagged in turn, which is correct.

**It is still correct.** Do not bump `updated`, because that would flag everything
downstream for a change that did not happen. Record the review instead:

```yaml
reviewed:
  05-information-architecture: "2026-09-30 labels renamed, structure unchanged"
```

The date must be on or after the upstream change and the reason must not be empty,
or the validator fails the pull request. The flag clears and nothing downstream moves.

## Superseded decisions

A decision is never edited. A new entry replaces it and names it in its
`Supersedes.` line. From then on every deliverable and rules page still citing
the old decision gets a warning, and the pull request that adds the new decision
gets a comment listing them with their owners. The answer is to re-read the
deliverable against the new decision and cite that instead. If the content had to
change, bump `updated` as usual, which flags its dependents. If it did not, the
citation swap is a front-matter-only edit and `updated` stays where it is.

Call files keep citing the decisions the call actually produced. They are history,
and they are not checked.

`depends_on` and `feeds` describe the same edge from both ends. The validator warns
when the two files disagree.

`status` reaches `confirmed` only through a merged pull request. Editing the
line by hand defeats the point of the word.

`updated` is the only date the staleness check reads. Git history is not used,
because a commit that only records a review would otherwise re-flag everything
downstream. To stop a forgotten bump from hiding a change, the pull request check
fails any deliverable whose content changed without `updated` moving. Edits that
touch only front-matter, such as a review or a Figma date, may leave it alone. A
date that already says today passes, because `updated` has day precision and
cannot move twice in one day.

## Calls

```yaml
---
kind: call
date: 2026-09-20
title: IA workshop
attendees: [franka, marko, client-rachel]
recording: https://drive.google.com/...     # never commit the recording itself
decisions: [D-021, D-022]
---
```

## Loose material, in `client/` and `research/`

One `README.md` per folder, not per file. A filename tells an agent nothing.

```yaml
---
kind: material
topic: xero-invoicing-api
added_by: marko
added: 2026-09-24
source: https://developer.xero.com/...
status: raw                                 # raw | worked-in
feeds: [07-technical-solution-proposal]
---

Two sentences on what this is and why we pulled it.
```

## The prototype manifest

`prototype/README.md` carries the prototype's own front-matter. It is a deliverable
like any other: it depends on everything it is built from, and 12-handover depends on
it. Any change under `prototype/` must move its `updated` date in the same pull
request, or the check fails. That date is how a change to the IA reaches the prototype.

## Prototype rules pages

```yaml
---
kind: rules
feature: orders-list
status: confirmed
decisions: [D-031]
covers: [states, long-text, data-shape, interaction, breakpoints]
---
```

`covers` is the playbook's five areas. The validator fails a feature that
claims `status: confirmed` without all five.

## Reserved values

- `owner`: `pm`, `designer`, `architect`
- `status` on a deliverable: `draft`, `in-review`, `confirmed`, `superseded`
- `status` on material: `raw`, `worked-in`
- `feeds` and `depends_on`: a deliverable id. The prototype is `10-development-ready-prototype`, with its own manifest at `prototype/README.md`.
